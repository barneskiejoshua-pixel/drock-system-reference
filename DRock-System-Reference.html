1. What DRock is and the bet it makes

DRock is a computer-use agent for one Windows PC. You type a request in plain English ("create notes.txt on the desktop with milk and bread", "why is billing.py returning 2", "what's using my disk"), and DRock does it with tools on the real machine, or answers it, or asks what you meant.

Most agents chase reliability with a bigger model. DRock makes the opposite bet. Its models are 0.6B to 4B parameters, they run on a 6 GB card, and nothing they say is treated as fact. A small model is fairly good at picking which operation to do next. It is bad at knowing whether that operation worked, and it will announce success after doing nothing. That one failure, false success, is what the whole system is built to make impossible.

Three rules follow, and almost every module exists to serve one of them:

  1. The model emits exactly one structured action per turn. One JSON object, decoded under a grammar, so a malformed action cannot even be produced.
  2. The model never verifies itself. The executor runs the action, re-reads the world, and hands the model the real result word for word.
  3. The model does not decide when the task is done. A deterministic gate (expect.py) reads what the request demands from its text, checks the verified trace, and refuses COMPLETE until the evidence exists.
The invariant. The completion gate may only ever grow stricter. A change that lets a previously failing trace pass is a regression. A labelled corpus (tests/test_gate_corpus.py) and a replay of every real task (drock audit) make that measurable.

Two more commitments shape the design. DRock is offline: no model call leaves the machine, and there is no bigger cloud model to escalate to. The only network traffic is a read the user asked for (a web search, a page fetch). And DRock reports what happened, including "I did X but could not verify it", which it never counts as done.

The pieces fall into five layers. Front doors take the line in (cli.py, chat.py, ui.py, console.py). Deciders work out what the line needs without a model where they can (macros.py, expect.py, depth.py, need.py, spell.py, verbs.py). The loop drives the model one action at a time (agent.py, model.py, schema.py, thought.py, lookahead.py). The boundary decides what may run and runs it (guard.py, policy.py, actions.py, integrity.py, snapshot.py, redact.py, untrusted.py). Records keep what happened and turn it into measurement (trace.py, events.py, latency.py, audit.py, stats.py, trust.py, corpus.py).

4. The life of one request

Take "please search the online news for trending topics", typed in the REPL.

  1. Read the line. ui.py owns the terminal. spell.py corrects a misspelt word only toward something DRock can check (a verb the gate knows, an installed program, a file in the folder). verbs.py holds the one table of surface verbs both the gate and the macros read.
  2. Chat or task. chat.Session.classify() runs a cascade of deterministic rules: follow-up questions ("why?", "show evidence"), questions about DRock, opinion and discussion questions, explicit commands. Only when nothing matches does it ask the model a two-way question under a binary grammar. This line is a task.
  3. Fast paths. Before any model call: is it answerable from verified memory? Does every clause match a macro rule? Is it a first-aid, mechanical or survival question, a calculation, a table query? Here an explicit web lookup compiles straight to SEARCH_WEB.
  4. Loop, if needed. Otherwise agent.Agent.run() routes to a tier (reflex for short open/close commands, coder for code words, mid for the rest), builds the prompt, and runs the loop in section 5.
  5. Every action passes guard.check (no provable no-ops), then policy.decide (risk tier, mode, protected paths), then the executor handler, which verifies its own effect.
  6. Stop. The task ends when expect.missing() is empty and the final answer survives expect.unfaithful(), or on a hard stop, which is reported as a failure in DRock's own words built from the gate's unmet list.
  7. Record. trace.py appends the goal, every action, every verified result, what the gate still wanted, and any action the user declined. activity.py prints the Inspected / Found / Changed / Validation report. latency.py logs where the seconds went.

5. The agent loop (agent.py)

The conversation the model sees is always the same shape: the system prompt (protocol and rules), then the system state, the facts DRock knows and the task, then alternating turns of its own action and a RESULT: {...} message carrying the executor's real output. It never sees its own summary of anything.

One step

PhaseCodeWhat happens
Observeobserve.snapshot(), memory.recall()Machine state and the few verified facts relevant to this goal
Thinkthought.pyThree sentences written before the model is called: what the request still needs, what the last step actually did, what follows. Built only from the gate's unmet list and the last step's verified flag, never from file contents
Planmodel.py, schema.pyThe model emits one action under a JSON-schema grammar; reason is the first property, so it states intent before it commits to an action name
Actguard.py, policy.py, actions.pyRefuse no-ops, check permission, run, verify
Gateexpect.missing()What the goal demands that the trace does not yet prove

Recovery, not escalation

There is no bigger model to hand off to. After three invalid outputs, three repeats of the same action, or three failures in a row, the loop restarts the conversation from a clean context (at most twice per task). The new context carries one sentence on what went wrong, the steps already verified, the actions that already failed with their errors, and what the gate still wants. A small model wedged in a bad frame often solves the same task cleanly on a second pass stripped of the confusion. This is the highest-leverage mechanism in the loop.

Loop guards

SituationResponse
A failed action proposed again unchangedResampled once, warmer, with the error in view; if identical again it is not run and the model is told why
Same action repeated, already succeededNot re-run; the model is nudged to the next step
Repeats three times, goal already satisfiedFinishes successfully: the model just failed to say COMPLETE
One action class fails twice with varied argumentsThat class is withheld from the grammar for one turn (thrash guard)
A package manager says a name does not existThat name is dead for that manager for the rest of the task
Three read-only steps repeating earlier calls with the same resultsSTALLED: the task stops and says so
Context filling up_fit() keeps the system prompt and task, drops the oldest exchanges, and notes what is already verified

Steering and refusing

The gate's unmet list is appended as Still missing: … after every turn, at the tail, where it cannot be trimmed and does not disturb the cache-stable prompt prefix. Before the first model call, expect.impossible() refuses a task the current mode cannot do at all (a write in readonly mode), in 0.00 s with nothing run. Grammar exclusions remove whole action families a goal has no business using: a read-only goal is offered nothing above LOW, an offline goal never sees the web actions, settings, Android and office actions appear only when the goal names them.

7. The executor (actions.py, 7,061 lines)

The executor is the only component that touches the machine and the only one allowed to say what happened. Every handler returns a Result:

FieldMeaning
okDid it succeed
verifiedWas the effect checked against the world afterwards; set only by an independent check, never because a command exited 0
verificationThe human-readable proof: "file exists, 3 lines, sha256 ab12…"
output / errorReal output and the real error, cut down to the useful line
changedWorkspace files a command actually changed (a stat diff of the tree before and after)
tests_ranHow many tests a runner reported running; "the tests passed" with zero tests run is not evidence

Verification is per action. A created file is re-opened and hashed; a move checks the source is gone and the destination exists; a Windows setting counts as changed only when Windows reads back the asked value; an installed program counts when Windows lists it; a GUI click is checked by re-reading the accessibility tree. journal.py adds the NTFS change journal as a second, kernel-side receipt for commands. snapshot.py copies what a MEDIUM or HIGH action is about to touch, so a change can be diffed and rolled back. integrity.py refuses a green test run that did not execute the program the task named (a stub, a copy, a shell builtin cannot stand in for it).

Forgiveness for form, never for substance. patching.py keeps a file's line endings, final newline and encoding on every edit and writes atomically. A near-miss edit can be repaired, and the trace says [MODEL ERROR repaired: …]; an unverified action is never made to look verified.

Foreign text is data. untrusted.py marks everything an action reads (a page, a file, a window's text) as content from outside the conversation, after a page that said "Ignore all previous instructions" was read by gemma3:4b as an order. redact.py replaces secret values before any tool output reaches the model, the screen or the trace.

Reading anything. formats.py extracts text from PDF, Word, Excel, PowerPoint, OpenDocument, EPUB, RTF, archives and SQLite with the standard library; fileinfo.py names a file's real type from its magic bytes; codeinfo.py gives a 4B model an outline with line ranges instead of 2,000 raw lines; tabular.py loads a table into in-memory SQLite so a sum or a maximum is computed, never guessed.

8. The completion gate (expect.py, 4,645 lines)

missing(goal, trace) is the stop decision. It reads the goal text and the verified trace, never the model's words, and returns the requirements still unproven. Each one is a sentence that goes straight back to the model, so the rule that blocks a false COMPLETE is also the rule that says what to do next.

RequirementRead from the goalSatisfied by
verb:<class>An imperative verb at a clause boundaryA verified action of that class (a command counts for a write only if changed is non-empty)
pathA path, or "called X", "named X and Y"A verified action naming it
under"subfolders inside it called A and B"Actions naming parent/child
plural"all the images", "every .jpg"As many verified moves as a verified listing showed
literal'quoted text', "containing: X", named columnsThat text in a verified action's parameters, still true at the end (freshness)
prints"prints X"A successful command whose output contains X
tests"run the tests", "make them pass"A runner reporting tests ran, green after the last edit
count"number of lines in X"A printed number matching a read of X
office, sorted, saved…Document, ordering and download wordsThe document's real structure, the rows' order, the file's bytes
questionA trailing ? with no action verbAt least one verified observation

Rules learned the hard way: a verb counts only at a clause boundary (", then run" once lost the run requirement and let a failing test run complete a task); evidence must be fresh (content written and then overwritten no longer counts); a proxy verification that reads the same whether or not the goal was reached is not evidence (OPEN_URL used to verify by "a browser process is running"); rhetoric ("make sure", "let me know") is stripped. Unknown is an outcome: when the action ran but its effect could not be confirmed, expect.unverified() names it and DRock says "did X but could not verify the outcome, so not claiming it".

The answer is checked too. expect.unfaithful() runs on every successful exit: a read-and-tell answer must occur in what was read, a list of .md files may name only .md files a listing showed. grounding.py applies the same idea to chat answers built from primers.

9. Policy, guard and the other safety layers

ModeLOWMEDIUMHIGH
ask (default)autoask once per action type per sessionask every time
autoautoautoask
yoloautoautoauto (sandbox and benchmarks only)
readonlyautodenieddenied
  • Protected paths refuse writes before any prompt: ~/.ssh and ~/.gnupg (reads too), system folders, Program Files, and DRock's own data/. A model that talks the user into "yes" still cannot write its own permission file, its trace log (the audit's proof) or its memory.
  • Shell commands are resolved word by word against the working directory, because three rounds of testing found three ways past a string match (echo > data/policy.json, a relative Windows path, a path inside a quoted Python one-liner). The stated limit: a path assembled at run time defeats any text inspection, and a test pins that as a known boundary.
  • Desktop input (click, type, keys) is HIGH and off unless "gui": true is set, because a click names no path and so escapes every path check.
  • guard.py refuses actions that are well-formed and allowed but provably useless: an edit whose old text equals its new text, a directory named like a file, a package name a manager already said it does not have, an absolute path the user never wrote (path fidelity).
  • Self-edits to DRock's own code always ask, in every mode. webinstall.py runs only signed installers and asks twice; portable.py extracts archives and never runs them.

10. Fast paths: answers with no model call

A small model spends two to four generations on "create a directory called notes", and each is a chance to go wrong. Rigid shapes compile instead. The executor still runs and verifies every compiled action under the same policy, and the task still cannot finish until the gate is satisfied, so a shortcut can never claim what the slow path could not.

Which shapes earned a rule was decided by the log: 623 of 3,561 recorded tasks were model-driven runs that used one kind of action. "Organize downloads folder" took 541 s and moved nothing through the model, and 1.3 s with every file sorted through the rule. The honest figure for the rulebook is the held-out one: it covers 12 of the 15 default benchmark goals but only 11 of 30 rewordings of them. So a rule is added for a shape, never for one sentence.

11. The conversation layer

chat.py (2,380 lines) is the front door for talk. Chat is answered free-form and streamed; tasks go to the agent; task results fold back into the conversation so "what did you just do?" works.

  • depth.py picks one of seven intents (DIRECT, EXPLAIN, DEEP_DIVE, LEARN, CREATE, EXECUTE, RESEARCH) and a budget rung from 80 to 900+ tokens in 0.7 ms, plus a one-line blueprint appended to the user message (never the system prompt, which would evict the prefix cache).
  • grounding.py turns retrieved primers into numbered facts; the model must answer from them and an invented claim is withdrawn. 98 offline primers cover big questions (philosophy, computing, science).
  • need.py reads what finished looks like when the words state a symptom ("billing.py returns 2, it should return 5"). english.py restates a multi-clause request as numbered clauses for the model only.
  • Clarifying questions: a request that names nothing ("whats new") is asked about: "Do you mean what's new in DRock, or today's news?"
  • prompt_budget.py holds ceilings for the prompts that decide the wait; the short chat prompt is about 174 units.

Backends. Ollama is the live backend (llama-server is blocked by Smart App Control). A Vulkan build serves the Arc on 127.0.0.1:11435 and the installer build on 11434 is the fallback. server.autostart() starts the Vulkan server when it is down; every fallback is printed and logged so a CPU run is never reported as a GPU run. native.py is DRock's own engine: a numpy transformer (GQA, RoPE, SwiGLU, fp16 KV cache, prefix reuse), a byte-level BPE tokenizer read from the GGUF (bpe.py) and constrained decoding by scaffolding (scaffold.py), checked token for token against Ollama. It also runs BitNet b1.58 through a numba int8 kernel at 6.9 tokens/s. It is a portability proof, not the default.

Determinism recipe. Every request carries seed: 0; servers DRock starts pin one slot, flash attention off and an f16 KV cache; the tier's context size never changes between calls. drock selftest --determinism sends three prompts twice and compares bytes. keep_alive is per caller: the agent holds a model for 30 minutes, probes and benchmarks run with DROCK_KEEP_ALIVE=0.

15. Remote AIs and the planner (opt-in only)

DRock's own tiers never leave the machine. One door was opened on 2026-10-07: a line that starts with /claude, /chatgpt, /gemini, /deepseek, /meta, /venice, /muse or /aimode goes to that service, and nothing else does. planner.py lets that remote model plan in DRock's action protocol while DRock validates, shows, asks, runs and verifies every step; HIGH actions are always asked. remote_web.py drives the chat sites over the Chrome DevTools Protocol in a visible browser; tribunal.py puts every relay in one conversation chaired by Claude; claudeskills.py lets those planners read Claude Code's installed skills.

19. Design rules

  1. The model never verifies itself. Ground truth is the executor re-reading the world.
  2. No escalation. Getting unstuck is a clean-context restart, not a bigger model.
  3. Fully offline. The one exception is a network read a task explicitly asks for; offline Wikipedia answers fact questions first.
  4. The completion gate may only grow stricter.
  5. Forgiveness for form, never for substance.
  6. A shortcut may not claim what the slow path could not.
  7. Report what happened. Nothing fakes success, DRock included.
  8. When unsure whether the user asked for something or about it, answer or ask; never act. A repeated request costs a turn; an unwanted action cannot be undone.
  9. A change somewhere is not a change here: verification checks the thing that should have changed.
  10. The answer is checked, not just the looking.

20. What the bugs taught

Each of these was found in DRock, most by running something rather than reading it. They share a shape: the code looks right, behaves the same every time, and destroys something.

  • A set of candidate paths let "rename old.txt to new.txt" swap source and destination.
  • p.startswith(base + "/") never matched a Windows path: every write in the workspace was refused and ~/.ssh was never protected.
  • A text-mode append rewrote every line ending in a file, and verification (which normalised CRLF) still said it was correct.
  • A same-size edit in the same second left __pycache__ valid, so the tests re-ran the bug that had just been fixed.
  • "bread. Then delete it." parsed Then as the verb, and a task completed having deleted nothing.
  • python calc.py exits 0 and changes nothing; a run "fixed" a bug that way. Hence changed.
  • "Find all .md files" ended, on a 0.6B model, with a WRITE_FILE over a real docs.md. Read-only goals now get nothing above LOW.

Safety properties decay the same way. The cloud-model guard was case-sensitive; the policy file's protection pointed at a folder the file had moved out of; the shell check assumed absolute paths, then assumed a path is its own word. Every one was found by executing the check. A guarantee nobody has run is not a guarantee.

22. Open work

  • Rollback instead of restart on recovery: snapshot.py has the mechanism; the call site in agent.py is not wired.
  • Deterministic search on low-margin turns (research/search.py) is designed and not wired; DROCK_SEARCH=1 changes nothing today.
  • Training on the trajectory log: the executor labels its own data, so rejection-sampling fine-tuning fits, but it is blocked on data volume.
  • Batched read-only observations (several CHECK_* in one turn).
  • OS control families F1 to F9 beyond settings (OS-CONTROL-PLAN.md).
  • Multi-bug debugging within the step budget; GPU stability on the A380 needs a driver newer than April 2023.
  • A known misreading as of today: "search github for trending python projects" picks SEARCH_IMAGES in 2 of 3 runs. NightShift takes it up tonight.
